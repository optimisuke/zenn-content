# はじめに

画像生成を使ったアプリでAPIのrequestが失敗したとき、どこまで自動でretryしてよいのか迷いました。画像APIが遅いうえ、その後にBlob保存とPostgreSQLへの生成ログ保存が続くためです。

この3つは1つのtransactionで囲めません。途中でサーバー側のFunctionが制限時間を超えると、どこまで終わったのか分からず、シンプルなretryでは画像の再生成やBlobの残骸が起こりそうです。

自分が作っているのは、最大10人ほどのワークショップで使うAI 4コマ漫画アプリです。Next.js、OpenAI API、Vercel Blob、Neon PostgreSQLという構成なので、まずは既存のPostgreSQLへ処理状態を保存することにしました。

アプリの操作やイベントで使った話は、[こちらの記事](https://zenn.dev/optimisuke/articles/e9d1ac3bd47482)にまとめています。今回は画像生成requestまわりに絞ります。

# 処理フローとtransactionの境界

外部APIとBlobはDBと一緒にrollbackできないため、画像APIを待つ間はPostgreSQLのtransactionを開きません。

![](/images/4e9c1a7b2d6f30/request-flow.png)

| 段階 | 処理                                             | transaction              |
| ---- | ------------------------------------------------ | ------------------------ |
| 1    | 画像APIを呼ぶrequestを1つに絞り、`pending`を保存 | PostgreSQLで短く確定     |
| 2    | 画像APIを呼ぶ                                    | DB transactionの外       |
| 3    | 画像をBlobへ保存                                 | DB transactionの外       |
| 4    | 生成ログを書き、requestを`completed`へ更新       | PostgreSQLでまとめて確定 |

PostgreSQLのrowを小さなステートマシンとして使い、同じ処理で画像APIを呼ぶrequestを1つに絞ります。途中で失敗した場合は、次のズレが残ります。

| 失敗地点             | 残り得る状態    | 扱い                                            |
| -------------------- | --------------- | ----------------------------------------------- |
| 画像API呼び出し後    | 画像APIだけ完了 | 同じ冪等性キーでは自動再生成しない              |
| Blob保存後、DB確定前 | Blobだけ残る    | 古い`pending`を失敗にし、孤立Blobは別途掃除する |
| DB確定後、response前 | DBは`completed` | 再送時に保存済み結果を返す                      |

# 外部サービス間の結果整合性

1つのNext.jsアプリでも、OpenAI API、Vercel Blob、Neonへ接続すれば処理は複数systemへまたがります。DB内の生成ログと状態更新はtransactionで確定し、外部サービスとのズレは後続requestやcleanupで収束させる、という整理です。

# PostgreSQLを選んだ理由

| 選択肢          | 今回の判断                                           |
| --------------- | ---------------------------------------------------- |
| Redisの`SET NX` | lock以外に結果と失敗履歴の保存先が必要になる         |
| 分散queue       | 最大10人の短時間イベントには運用が重い               |
| PostgreSQL      | 既存DBで重複呼び出し、状態、結果をまとめて管理できる |

結果と失敗履歴も必要で、高頻度な処理でもないため、既存のPostgreSQLへ寄せるのが一番しっくりきました。

# request状態の定義

状態は`pending / completed / failed`の3つです。`timeout`のような失敗理由をstatusへ混ぜず、`failureCode`へ分けます。

![](/images/4e9c1a7b2d6f30/state-machine.png)

```prisma
model ImageAiRequest {
  idempotencyKey String   @id
  status         String   @default("pending")
  resultJson     String?
  failureCode    String?
  retryable      Boolean  @default(false)
  updatedAt      DateTime @updatedAt

  @@index([status, updatedAt])
}
```

画像本体はBlobへ置き、`resultJson`にはBlob pathやgeneration IDだけを保存します。Blob保存と生成ログのDB transactionが終わったら`completed`にします。

# 冪等性キーの設計

コード上の`idempotencyKey`には、生成内容を同じ順序で文字列化し、SHA-256でハッシュ化した値を使います。材料は数KB程度なので、計算負荷はほぼ無視できます。

```ts
const key = createImageRequestKey({
  draftId,
  generationAttempt,
  kind,
  position,
  prompt,
  styleReferenceBlobPaths,
});
```

| 冪等性キーの材料           | 役割                           |
| -------------------------- | ------------------------------ |
| `draftId`、`position`      | どの作品・コマか               |
| `kind`、`prompt`、参照画像 | 何を生成するか                 |
| `generationAttempt`        | 利用者が明示的に再生成した回数 |

機械的な再送では同じ冪等性キーを使い、利用者が「もう一度つくる」を押したときだけ`generationAttempt`を増やします。これで、通信上のretryと新しい生成依頼を分けられます。

# 同時requestから画像APIを呼ぶ1件を選ぶ

同じ`idempotencyKey`は2件保存できないようにし、最初にrowを作れたrequestだけが画像APIを呼びます。コード内部ではこの判定結果を`owner`と呼んでいますが、利用者や`ownerId`を保存しているわけではありません。後続requestは既存rowを読みます。

| DBの状態            | response                        | 画像API             |
| ------------------- | ------------------------------- | ------------------- |
| `completed`         | 保存済み結果を返す              | 呼ばない            |
| `pending`           | `409 + Retry-After`             | 呼ばない            |
| retry可能な`failed` | 条件付きupdateで`pending`へ戻す | 選ばれた1件だけ呼ぶ |
| retry不可の`failed` | 失敗として返す                  | 呼ばない            |

retry可能な`failed`も、古いstatusと`retryable`を条件にした`updateMany`で、画像APIを呼べるrequestを1つに絞ります。

# 古い`pending`のtimeout判定

一番なやんだのが、「タイムアウトした古い`pending`を誰が管理するのか」でした。timerやcronは置かず、次のrequestが`updatedAt`を見て`failed / timeout`へ変えます。

![](/images/4e9c1a7b2d6f30/retry-decision.png)

70秒は`maxDuration = 60`秒へ余裕を足した値で、自動再生成の根拠にはしません。`Retry-After: 10`も状態を再確認する目安です。timeout後は、利用者が「もう一度つくる」を押したときだけ新しいattemptを始めます。

# 失敗地点とretry可否

同じ冪等性キーでretryするのは、入力チェックなど、画像APIを呼ぶ前に失敗した場合だけです。呼び出し開始後は、自動でretryせずにユーザーにエラーをだしてretryしてもらうことにしました。そのほうがシンプルだし、ユーザーも失敗したことがわかりやすいかなと思い。

# 状態を持つことのtrade-off

正直、状態を持つことで別のバグが増えそうな気がしてもやもやしてます。`pending`が残る、statusとBlobがずれる、といった問題です。それでも途中失敗を扱うにはどこかに状態が必要なので、今は既存のPostgreSQLへ寄せるのが一番マシかなーという判断です。

# テストと運用

同時requestでも画像APIを呼ぶのが1件だけになること、`completed`なら保存済み結果を返すこと、Blob保存後のDB失敗では自動再生成しないことをテストしました。

# おわりに

DB transactionを短く保ち、冪等性キーと3つの状態で外部サービス間のズレを扱う形が、今回の規模には良さそうです。ただ、体系的に調査したというより、実装を見ながらAIと会話して整理した設計です。画像API側の冪等性キーやtransactional outbox、queueなど、もっと良い方法があればぜひ教えてほしいです。
