# はじめに

Vercel、Neon、OpenAI、Cloudflareを使って個人開発をしていると、認証情報がじわじわ増えてきます。

OpenAIのAPIキー、Neonの接続URL、CLIのログイン情報、CI用トークン。最初は全部まとめて「Secret」と呼んでいたんですが、とりあえず`.env.local`へ入れていると、いろいろあってよく分からなくなってきました。

ということで、今は **アプリ用Secret、ローカルCLIのログイン、CI用トークン** を分けることにしました。あたりまえかもですが。。。あとは、macOS Keychainを手元の投入元にするしたら、いい感じなきがしてるので、今の運用を整理します。
組織のSecret管理基盤を置き換える話ではありませんが、小さいプロジェクトの参考になればと思います。

コマンド例はmacOS向けで、各サービスとCLIの準備は終わっている前提です。

# 先に、3種類へ分ける

![](/images/d7a4c2e91f6b30/credential-flow.png)

| 種類                      | 置き場所                         |
| ------------------------- | -------------------------------- |
| アプリ用Secret            | Vercelなど実行環境のSecretストア |
| ローカルCLIのログイン情報 | 各CLIが管理する保存先            |
| CI用トークン              | GitHub Environment Secrets       |

Keychainには全部を集めず、自分で発行したAPIキーの原本だけを置きます。

# `.envl`を保管庫にしない

`.env`や`.env.local`はローカル実行には便利ですが、（できるだけ）Secretの原本にはしないことにしました。Git管理から除外していても、エディタ、バックアップ、検索、AIコーディングエージェントなどから読める範囲が広がるためです。

# APIキーはKeychainを投入元にする

OpenAIのAPIキーのように、自分で発行して設定する値はmacOS Keychainへ置くことにしました。値をコマンドへ直接書かず、対話入力します。

```bash
security add-generic-password \
  -U \
  -a "$(id -un)" \
  -s "comic-app-openai-preview" \
  -w
```

`-w`を最後に置くと値の入力を求められるので、APIキーがコマンド履歴へ残りません。service名は`<アプリ>-<用途>-<環境>`にしています。

```text
comic-app-openai-preview
comic-app-openai-production
```

`-U`を付けると、同じserviceとaccountの項目があれば更新されます。

cliでVercelへ設定するときは、Keychainから標準入力へ直接渡せます。長くて、覚えられなくて打つのが面倒ですが、AIがやってくれるので問題ないです。

```bash
security find-generic-password \
  -a "$(id -un)" \
  -s "comic-app-openai-preview" \
  -w \
  | vercel env add OPENAI_API_KEY preview --sensitive
```

更新時は`env add`を`env update`へ置き換えます。`echo`や一時ファイルは不要ですが、パイプ先のCLIが入力をログへ出さないか、最初はダミー値で確認しています。

# CLIログインはAPIキーと分ける

Vercel、Neon、Cloudflareを自分やAIが操作するときは、対話ログインを使います。

```bash
vercel login
neon auth
wrangler login --use-keyring
```

CLIのログイン情報は、アプリへ渡すAPIキーとは別物です。自分で取り出してCIへコピーせず、CLIに管理を任せます。Neonで認証が切れたときも、DBパスワードを作り直すのではなく`neon auth`をやり直せば済みました。

保存方法はCLIごとに違います。Wranglerは`--use-keyring`を付けると認証情報を暗号化し、その暗号鍵をOSのKeychainへ置きます。保存先は次で確認できます。

```bash
wrangler whoami
```

一方、`terraform login`はデフォルトでトークンを`credentials.tfrc.json`へ平文保存するみたいです。対話ログインだからKeychainへ入る、とは限らないので、導入時に保存先とlogout方法を確認しています。

# ローカルログインをCIへ持ち込まない

CIには用途と権限を絞った専用トークンを発行し、GitHub Environment Secretsへ置きます。たとえばCloudflareのDNS変更はTerraformを正にして、Wranglerのログイン情報ではなく、AccountやZoneを絞った`CLOUDFLARE_API_TOKEN`を使っています。

GitHub Secret名と、providerが読む環境変数名が違う場合は明示的につなぎます。

```yaml
env:
  NEON_TOKEN: ${{ secrets.NEON_API_KEY }}
```

自分はNeonのトークンが別Organizationを対象にしていて、`project not found`にもなりました。こういう凡ミスが起こりにくい仕組みを作りたいけど思い付いてません。。。

# AIコーディングエージェントには値を渡さない

AIコーディングエージェントには、環境変数名、配置、疎通確認を任せます。Secretの実値をチャットへ貼る、`.env`を読ませる、Keychainから取り出させる、といった操作はせず、投入は人が行うことにしました。

# おわりに

Sercretを整理して、Keychainを使えば全部安全になるわけでも、CLIログインなら保存先を気にしなくてよいわけでもありませんが、アプリ、人、CIで認証情報を分けると、交換したり、入力するときにあまり迷わなくなりました。安心感があがったのが満足度高いです。ただ完璧ではない気がするので、他に良いやり方知ってる方いればぜひ教えてください。
